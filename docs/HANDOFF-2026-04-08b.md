# Handoff — 2026-04-08 (session 2)

## What was done this session

### Pad baseline calibration fix (`mk1-usb/mk1_device.c`)
Resting EP4 pad reports have a distinctive pattern: pair K = K×0x1000, channel B
mirrors channel A. This matches the `mk1_is_scanned_button_report` filter exactly,
so resting reports were being silently discarded before the baseline capture code ran.
`pad_baseline_set` stayed false until the first actual pad press, which was captured
as "resting baseline" — making all pads appear stuck at max pressure at startup.

Fix: capture baseline from the first scan-table (resting) report, then continue
discarding subsequent scan-table reports as before.

### Pad pressure throttle (`mk1-bridge/main.c`)
EP4 fires at ~700 Hz. Previously, every ADC change (including noise while a pad is
held) was forwarded as a `NI_EVT_PAD_DATA / pressure_update` IPC message. This
flooded the CFMessagePort queue causing Maschine to lag and eventually stop
responding temporarily.

Fix: a `g_sent_pressure[16]` array tracks the last pressure value forwarded. A
`pressure_update` is only sent when the new value differs from the last sent by ≥200
counts (~5% of full 4095 range). `hit_on` and `hit_off` transitions are always sent
immediately regardless of threshold.

### Status screen (`mk1-bridge/main.c`)
Displays "Open" / "Maschine" (two lines) on both LCD screens when:
1. The USB device is opened but Maschine is not yet connected
2. Maschine exits (detected by polling `pgrep -x 'Maschine 2'` every 2 s)

Implementation: minimal 5×7 bitmap font, rendered at 3× scale into the 255×64
logical-pixel ST7529 framebuffer (170 bytes/row, 3 px packed per 2 bytes), sent
to both displays via the same EP8 RAMWR path as `forward_display`.

## Open issues

### 1. Pad rubber LEDs not lighting up

**Symptom**: When pads are pressed, button LEDs light up correctly (e.g. pad 3 press
flashes Group G — this is intentional Maschine behavior). But the rubber pad LEDs
(the physical silicone pad surfaces) never light up at all. They DO work on Intel Mac
with the original NIHA.

**What we know**:
- IPC `NI_CMD_LED` payload: current Maschine (Apple Silicon) sends 57 bytes; we inject
  `logical[37+K]` → `phys[17+K]` for K=0..15 (pad rubber LEDs), then send 34-byte EP1
  DIMM_LEDS packet `[0x0c, phys[0..32]]`.
- Button LEDs at phys[0..16] work fine in the same packet.

**Intel IPC sniffer analysis (session 3) — completed**

Capture: `build/Debug/logs-from-intel/mk1-ipc-sniffer.log`
Session: pressed pads 1–16 one at a time, each rubber LED lit and turned off after release.
Intel Mac was running the current Maschine version (new format, 57-byte LED payload).

Key finding: **rubber LED IPC positions are constant across ALL pad presses.**
For every pad pressed (14 of 16 captured), the LED message shows:
- `logical[38] = 0x13` (dim, constant)
- `logical[39] = 0x32` (dim) → `0x3f` (bright, tracks pressure)

These values NEVER shift to reflect which physical pad was pressed. This invalidates the
per-pad array model (`logical[37+N]` = pad N rubber).

**Button (GROUP) LED per pad press** (changes correctly per pad):

| pad_index | pad | button logical[] | phys[] | label |
|-----------|-----|-----------------|--------|-------|
| 0  | pad 1  | logical[15] | phys[14] | Browse |
| 1  | pad 2  | logical[14] | phys[15] | Sampling |
| 2  | pad 3  | logical[13] | phys[16] | Modules Left |
| 3  | pad 4  | logical[12] | phys[9]  | Group D |
| 4  | pad 5  | logical[11] | phys[10] | Skip |
| 5  | pad 6  | logical[10] | phys[11] | Auto Write |
| 6  | pad 7  | logical[9]  | phys[12] | Group A |
| 7  | pad 8  | logical[8]  | phys[5]  | Left navigation |
| 8  | pad 9  | logical[7]  | phys[6]  | Group E |
| 9  | pad 10 | logical[6]  | phys[7]  | Group F |
| 10 | pad 11 | logical[5]  | phys[8]  | Group C |
| 11 | pad 12 | logical[4]  | phys[1]  | dead |
| 12 | pad 13 | logical[3]  | phys[2]  | Group G |
| 13 | pad 14 | logical[2]  | phys[3]  | Group H |
| 14 | pad 15 | logical[0]  | phys[0]  | control reg |
| 15 | pad 16 | (not captured) | — | (Group B expected) |

Pattern: `pad_index N → logical[15-N]` for N=0..13, with gap at logical[1].

**Idle LED background state** (always non-zero in Intel trace):
- `logical[47]=0x32, logical[50]=0x32, logical[51]=0x13, logical[52]=0x13`
- `logical[53]=0x32, logical[54]=0x13, logical[55]=0x13`
These are persistent mode/group indicators in the UI, not pad-press artifacts.

**Conclusion**: The rubber LED mechanism is NOT the per-pad DIMM_LEDS array model.
Real NIHA on Intel translates the constant `logical[38]/[39]` into per-pad hardware
commands through a mechanism invisible to the IPC sniffer. Possibilities:
- NIHA tracks which pad is currently active from the PAD_DATA events and injects
  the correct phys position itself, ignoring the IPC logical position entirely
- Rubber LEDs use a different EP1 command (not 0x0c) or a different payload structure
- The `logical[38]/[39]` values are "current active pad" brightness scalars, and NIHA
  derives which `phys[17+N]` slot to write from its own pad-press state machine

**Next step (definitive)**: USB pcap on Intel Mac during pad presses. Wireshark capture
of EP1 output bytes while pads are lit will show exact phys byte positions NIHA writes.
Compare to what our bridge sends.

**Interim experiment**: Temporarily hard-code the bridge to send `phys[17..32] = 0x5c`
unconditionally on every DIMM_LEDS write, regardless of IPC data. If rubber LEDs light
up, the hardware does respond to phys[17+N] and the problem is our IPC→phys mapping.
If nothing lights, rubber LEDs use a different command entirely.

### 2. Display backlight toggles off briefly on button presses

**Symptom**: Both displays simultaneously go dark for ~1 frame when screen-area or
group buttons are pressed (view transitions in Maschine). Pixel content is preserved —
only the physical backlight LED toggles. Confirmed on both displays simultaneously.

**What we know / have ruled out**:
- NOT caused by: `0xaf` re-assertion after RAMWR, all-black frame skipping, phys[1]
  forcing in DIMM_LEDS, adding `0x30` before address window (reverted — made things worse).
- Happens in sync with view-transition display updates from Maschine — suggests it's
  triggered by something in the display command sequence, not the LED command.
- pcap steady-state frames: real NIHA sends `0x75 + 0x15 + RAMWR` only (no `0x30` prefix).
  Our bridge follows this exactly.
- The original kext/NIHA on Intel Mac does not exhibit this — so either the kext sets
  up display state we don't replicate, or the Apple Silicon USB timing is different.

**Leading hypotheses**:
1. Maschine sends an all-black frame (view clear) before the new view content. Our
   bridge skips all-black frames in `forward_display`, but maybe a partial all-black
   is slipping through.
2. The ST7529 controller is briefly entering sleep or power-save mode in response to
   some command byte in the Maschine display stream that we forward blindly.
3. The RAMWR sequence briefly disables the backlight during pixel write — a hardware
   timing issue specific to Apple Silicon USB latency. The original kext was synchronous
   via IOKit and may have had tighter timing.

**Next steps**:
- Log every display command byte sequence around a button press to see if any unusual
  ST7529 commands (e.g. display-off `0xae`, sleep-in `0x95`) appear in the stream.
- Try adding a small delay before sending RAMWR to see if it's a timing issue.
- Check whether the backlight is controlled by the `0xaf` (display ON) command and
  whether it needs to be re-sent after certain operations.

### 3. Bridge reconnect is slow (~30s)

**Symptom**: If the bridge is killed while Maschine is open and restarted, the bridge
sends `DEVICE_OFF` to Maschine's old notification port. Maschine processes this and
eventually retries the `NIHWMainHandler` handshake, but takes approximately 30 seconds.

**Status**: Known limitation. Workaround: restart Maschine manually for instant recovery.
The mechanism (save session → send DEVICE_OFF on restart → poll for reconnect) is
implemented and functional; the delay is on Maschine's side and not easily controllable.
