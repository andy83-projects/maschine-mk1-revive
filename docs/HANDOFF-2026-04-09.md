Full analysis of `build/Debug/logs-from-intel/mk1-ipc-sniffer.log` for all 16 pads (14 captured).

### Frida kext hook — completed

Ran `led_capture.js` on Intel Mac against live NIHA, capturing selector 6 calls to the kext.

**Confirmed**:

phys[24]=0x32, phys[25]=0x13, phys[26]=0x13, phys[28]=0x5c (pad 12 bright).

### EP1 33-byte hardcoded test — FAILED

Sent the exact Frida full-state pattern as a 33-byte EP1 packet from our bridge.
Hardware did **not** respond — rubber LEDs did not light up on any pad.

**Conclusion**: The hardware requires kext-level initialization to enable rubber LED PWM
mode. Simply sending the correct EP1 byte pattern is insufficient. The kext sends an EP1
command during driver attach (before any `IOConnectCallMethod` user-client call) that puts
the rubber LED controller into an active mode. This command is **not capturable** via an
`IOConnectCallMethod` hook.

### `mk1-bridge/main.c` — `forward_led` reverted to clean state

## Open issues

### 1. Pad rubber LEDs not lighting up

**Root cause (hypothesis)**: The kext sends an EP1 command during driver attach (before
any user-client `IOConnectCallMethod` call) that enables rubber LED PWM mode. This is the
only un-examined initialization path.

**Evidence**:
- Correct 33-byte EP1 pattern confirmed via Frida kext hook
- Sending that exact pattern from our bridge produces no rubber LED response
- Hardware does respond to button/group LEDs in the same packet → EP1 write path is working
- The kext init path (not capturable via `IOConnectCallMethod` hook) is the remaining candidate

**Next step — all-selector init capture**:

SCP updated script to Intel Mac and run from NIHA startup:
```bash
scp mk1-trace/led_capture.js oldmac:~/
# On Intel Mac:
sudo killall NIHardwareAgent; sleep 1; frida -n NIHardwareAgent -l ~/led_capture.js 2>&1 | tee ~/led_capture2.log
```
Run through: startup → Maschine connects → press one pad → Ctrl-C → copy log back.

Look for:
- Any selector number **not in {3, 5, 6, 7, 17, 18, 19, 21}** during startup
- Any selector 6 call at init with struct content different from steady-state packets
- Any scalar-only call with unusual values

**Alternative approach — hook EP1 writes directly**:
Instead of hooking the user-client (`IOConnectCallMethod`), hook the kext's internal
bulk-write function to see ALL bytes sent to EP1, including driver-attach init commands.
This requires finding the kext symbol (e.g., via `kextstat` + binary RE).

**Alternative approach — replay raw init from bridge**:
Find the init EP1 command by binary RE of the kext (`/System/Library/Extensions/` or
`/Library/Extensions/` on Intel Mac), then send it from our bridge at device open time
before the first LED update.

### 2. Display backlight toggles off briefly on button presses

**Symptom**: Both displays go dark for ~1 frame on screen-area/group button presses.
Pixel content preserved — only physical backlight toggles. Happens on view transitions.

**What we know / ruled out**:
- NOT: `0xaf` re-assertion after RAMWR, all-black frame skipping, phys[1] in DIMM_LEDS,
  `0x30` prefix before address window (tested and reverted).
- Follows Maschine display update timing → triggered by display command sequence, not LED.
- Real NIHA on Intel does not exhibit this.

**Leading hypotheses**:
1. All-black frame (view clear) partially slipping through `forward_display` filter
2. ST7529 entering sleep/power-save from some command byte in Maschine's stream
3. Apple Silicon USB timing vs. synchronous IOKit in original kext

**Next steps**:
- Log every display command byte sequence around a button press; look for `0xae` (display-off)
  or `0x95` (sleep-in) in the stream
- Try small delay before RAMWR to test timing hypothesis
