# HANDOFF 2026-04-13d — First press missed after fresh Maschine launch

## Summary

One functional issue remains after the current bridge work:

- on a fresh launch of Maschine, the very first button press or pad hit is
  consistently missed
- the software does not react to that first hit
- the corresponding button or pad LED also does not light on that first hit
- the second press works normally

This appears to happen once per new Maschine launch, not continuously during
normal use after the first successful interaction.

---

## Current observed behavior

The bridge is not totally blind to input:

- button and pad traffic does appear in the bridge logs
- after the initial missed interaction, subsequent presses behave normally

That makes this look less like a raw USB decode failure and more like a
startup / handshake / readiness ordering problem.

---

## What was already tried

This session tried one targeted fix:

- added `mk1_server_is_input_ready()` and changed `on_pad()` / `on_button()` to
  wait for `inst_connected` instead of the older `dev_connected ||
  inst_connected` condition

Reason for that attempt:

- the device-phase handshake comes up before the full instance-side event path
  is ready
- if the bridge starts forwarding too early, the first event could be sent to a
  notification port that Maschine is not yet actually using for UI input

Result:

- build succeeded
- user retest says the issue still happens

So the bug is not fully explained by the simple "wrong notification port too
early" theory.

---

## Best current hypothesis

The most likely remaining causes are:

1. A startup-state transition inside Maschine where early input is accepted by
   the transport layer but ignored by the app until a later command or focus
   state completes.
2. A missing synthetic event from our side after connection, such as a state or
   focus transition that the real NIHardwareAgent sends before the first human
   input becomes actionable.
3. A first-event edge case in our own event stream, where the first pad/button
   packet after startup lacks some expected baseline or ordering relative to
   `DEVICE_ON`, `START`, `INSTANCE_NAME`, or `SETFOCUS`.

There is also a separate pad-input quality issue reported later:

- rogue pad hits sometimes appear on pads far away from the one being struck

Current read on that issue:

- this looks more like raw pressure crosstalk / over-eager hit promotion than an
  IPC wire-format problem
- the USB path supplies all 16 pad pressures every EP4 frame
- the bridge currently converts every pad that crosses `PAD_HIT_ON_THRESHOLD`
  into a real `HIT_ON`

---

## Rejected filtering idea

A short-lived experiment tried this approach conceptually:

- if multiple pads crossed hit-on in the same EP4 frame, keep the strongest hit
  and suppress weaker candidates as crosstalk

Why it seemed plausible:

- the logs show multiple pads crossing threshold in the same interaction
- some of the extra hits are much weaker than the dominant one

Why it was rejected:

- this would break legitimate two-pad and three-pad playing
- “strongest hit wins” is the wrong behavioral model for a pad controller
- even a softer version of that idea risks suppressing intentional chords,
  flams, and simultaneous pad combinations

Important:

- do not reintroduce a global strongest-hit suppression filter
- any future crosstalk mitigation must preserve intentional multi-pad hits

---

## Better next step for rogue pad hits

Before changing behavior again, add logging / capture around full 16-pad pressure
frames so we can compare:

- one intentional single-pad strike
- one intentional two-pad strike
- one real-world rogue-hit case

The next filter, if any, should be based on actual onset shape and relative
strength over multiple frames, not a blanket “only strongest simultaneous hit
counts” rule.

## Recommended next debugging steps

Do these in order.

### 1. Add explicit handshake and first-input timing logs

Add precise bridge-side logs for:

- device ACK completion
- instance ACK completion
- `DEVICE_ON` send
- `START` receive / reply
- `INSTANCE_NAME` receive / reply
- `SETFOCUS` push
- first pad event seen from USB
- first button event seen from USB
- first pad/button event successfully pushed to Maschine
- first LED/display command received back from Maschine after connection

Goal:

- establish the exact ordering between connection milestones and the first
  ignored human interaction

### 2. Capture whether the first missed input is actually pushed successfully

Instrument `mk1_server_send_event()` / `push_event()` to log:

- target port used
- message id
- send success/failure
- whether the event went to instance or device notification port

Goal:

- determine whether the first event is dropped inside the bridge or accepted by
  the bridge and ignored by Maschine

### 3. Compare first-missed button press against first-missed pad hit

Run two clean tests after fresh Maschine launch:

- first interaction = a transport/group/button press
- first interaction = a pad hit

Goal:

- if both fail identically, that points to handshake/focus/app readiness
- if only pad fails, revisit pad-state initialization
- if only button fails, revisit button event format or control-state baseline

### 4. Consider a short post-connect input gate only if logs justify it

If the logs show Maschine becomes functionally ready a small fixed time after
the bridge marks connection complete, add a temporary gated delay or deferred
"input armed" transition after the final instance-side handshake event.

This should be evidence-driven, not guessed.

### 5. If needed, compare against a known-good NIHA launch trace

If local instrumentation is not enough, capture a known-good startup trace from
the original path and compare:

- order of `DEVICE_ON`
- timing of `SETFOCUS`
- any other synthetic state events before first actionable input
