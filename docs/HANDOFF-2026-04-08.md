## Known issue: display backlight toggles on button presses

### Symptom

When pressing screen-area or group buttons (which trigger view transitions in the
Maschine software), both displays simultaneously go dark for ~1 frame then recover.
The pixel content is still present (visible in ambient light) — only the physical
backlight LED is toggling. Both displays go off at the same time, confirming a single
shared control.

### What was tried

All of the following were tested on hardware and confirmed NOT to fix it:

1. **`0xaf` after each RAMWR** — added Display ON after every frame write. No effect.
2. **Skipping all-black pixel updates** — Maschine sends all-zero frames during view
   transitions; skipping them prevents the RAMWR but didn't stop the toggle.
3. **Forcing phys[1] = 0x1e** — hypothesis that phys[1] in DIMM_LEDS controls the
   display backlight. No effect.
4. **`0x30` before address window on each frame** — re-asserting extension mode before
   `0x75`/`0x15`. No effect; subsequently reverted (pcap shows this is wrong anyway).
5. **Removing `0x30` before address window** — current state. Matches pcap behavior
   for steady-state frames. Still no fix.

### Current code state (2026-04-08 end of session)

`forward_display` in `mk1-bridge/main.c`:
- Composites partial pixel updates into `g_display_fb[]` full framebuffer
- Skips all-black pixel updates (returns early)
- Sends: `0x75 0x00 0x3f`, `0x15 0x00 0x54`, then full RAMWR (no `0x30` prefix)
- Does NOT send `0xaf` after RAMWR

### Pcap findings from this session

`ep08.txt` (Intel Mac capture) reveals the real NIHA's per-frame EP8 sequence:

**First frame (init → UI mode transition):**
1. Display 0 init: 17 commands ending with `0x81 0x20 0x02` (no `0xaf` in init)
2. Display 2 init: same 17 commands
3. Display 0 address window: `0x75 0x00 0x3f`, `0x15 0x00 0x54`
4. Display 0 RAMWR: `0x5c` + 10880 bytes (all `0xf8` = white)
5. Display 2 address window + RAMWR (same)
6. `0xaf` (Display ON) for display 0
7. `0xaf` (Display ON) for display 2

**Second frame (animation→UI DSCANSET transition, one-time):**
Full re-init sequence including: `0x94` (sleep out), `0xbc 0x00 0x01 0x02`
(intermediate DSCANSET), standalone `0x5c`, `0x25`, `0xaf`, then `0xbc 0x02 0x01 0x01`
(UI mode), `0xa6`, `0x81 0x25 0x02` (contrast), address window, full RAMWR.
This one-time transition exists because the Intel Mac pcap init used animation mode
(`0xbc 0x00 0x00 0x02`). Our init already uses UI mode, so this transition is not needed.

**Subsequent frames (steady-state):**
`0x75 0x00 0x3f`, `0x15 0x00 0x54`, RAMWR only. No `0x30`, no `0xaf`.
This is what we now do — matches pcap. Still doesn't fix backlight.

### Leading hypotheses for next session

**Hypothesis A — caiaq firmware backlight GPIO (most likely)**
The physical backlight is a GPIO/PWM on the caiaq chip, separate from the ST7529.
It may be controlled by an EP1 command we haven't identified. The EP1 command log
(`led.log`) during a backlight toggle could reveal an unexpected byte pattern.

Action: capture `led.log` and `display.log` during a toggle event. Look for any EP1
command other than DIMM_LEDS (0x0c), or an unusual DIMM_LEDS payload.

**Hypothesis B — Maschine sends an unhandled IPC command type**
If Maschine sends a command type that isn't NI_CMD_DISPLAY or NI_CMD_LED, our `on_cmd`
callback logs it but does nothing. If that unknown command is a "display backlight" or
"display off" command, we'd see it in `bridge.log` as "unhandled CMD 0x...".

Action: check `bridge.log` after triggering the toggle. Look for "unhandled CMD" lines
that correlate with the dark flash.

**Hypothesis C — EP8 sequence needs the `0xaf` sent after the FIRST RAMWR**
Our init sends `0xaf` at the end (before any RAMWR). The pcap shows `0xaf` sent AFTER
the first RAMWR. Could be the display needs to latch a full frame before enabling.
We could try: remove `0xaf` from init, add a post-RAMWR `0xaf` only for the first frame.

**Hypothesis D — display voltage sag during large EP8 + EP4 simultaneous transfers**
During a view transition, Maschine sends a 10880-byte display update (EP8) while EP4
is continuously reading pad data. USB bus contention might cause a voltage droop that
briefly kills the backlight. Very unlikely with modern USB controllers but worth noting.

### Files to look at next time

- `bridge.log` — "unhandled CMD" lines (Hypothesis B)
- `led.log` — DIMM_LEDS payload at the moment of toggle (Hypothesis A)
- `display.log` — which display updates are sent around the toggle (skips shown)
- `ep08.txt` lines 3035-3099 — the standalone `0x5c` + `0x25` sequence in full detail
  (could `0x25` be a backlight control command sent to the caiaq firmware?)
